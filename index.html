What goes in and what comes out

A decision surface, not another brainstorming session.

PA_PVP turns unresolved material into an operational state that can advance, park, probe, close, or be discarded.

INPUT

Give it the unresolved object.

  • a plan with uncertain dependencies;
  • an artifact that needs adversarial review;
  • a choice with competing viable options;
  • a target plus an evaluation method;
  • a previous PA_PVP snapshot to continue.
OUTPUT

Get a state you can act on.

  • a forced verdict;
  • one concrete [NEXT] action;
  • observable or measurable steps;
  • evidence limits and open uncertainty;
  • a reusable machine snapshot plus human table.

The result

Three verdicts. No “it depends.”

Uncertainty must become a next action, a parked condition, a probe, or a discard rule.

⚡

DO NOW

The item is active and has an executable next move.

🕓

DO LATER

The item is parked until a condition, dependency, date, or evidence requirement changes.

🗑️

DISCARD

The item should not proceed under the current state.

Valid output anatomy

Read the human view. Reuse the machine state.

A valid decision response begins with STATE: DECISION.TEST.FINAL. The code block is the reusable state; the table after it is only a scanning surface.

  • [QUEUE] exposes state transition, verdict, gate, and first step.
  • [NEXT] names exactly one emitted action.
  • Invalid output remains diagnostic and must not be reused.

Where it helps

Use it where plausible work must become operational.

PLANS

Pressure-test dependencies, rollback, sequencing, and kill conditions.

ARTIFACTS

Audit prompts, protocols, code, documents, specifications, and designs.

CHOICES

Close trade-offs or define the smallest useful evidence probe.

PROJECTS

Reduce too many possible next steps to one bounded move.

EXPERIMENTS

Make reversible tests explicit, measurable, and terminable.

CONTINUATION

Advance prior state without reconstructing the decision from scratch.

Practical limits

A protocol is not a runtime, an oracle, or a certification.

PA_PVP can structure decisions, simulations, probes, and next steps. Real execution still depends on the AI host, available tools, permissions, and external systems.

  • Simulated evidence is not real-world evidence.
  • External facts are not current unless inspected.
  • High-stakes or irreversible decisions may require real evidence and specialist review.
  • “PLUTONIUM-like” is a project identity and design metaphor, not a safety certification.

Formal input modes

PLAN

Steps, options, or an implementation plan.

ARTIFACT

A prompt, document, protocol, code sample, or specification.

TOOL + TARGET

A named evaluation method applied to a specific target.

PREVIOUS STATE

A prior valid snapshot for continuation.

State and closure

Core states include DRAFT, ACTIVE, STANDBY, PROBING, CLOSED, EXPIRED, and DISCARDED.

ct:SIM marks simulated closure. ct:REAL requires historical, real, or experimental evidence. Irreversible or REAL_ONLY decisions cannot close as simulated.

Gates, probes, and invalid output

Dominant gates route the item through fail-fast, falsification, debt, fragility, dependency, confidence, external-block, redesign, score-triage, or no-gate behavior.

Reality probes must expose a target driver, observable result, timebox, kill switch, and representativeness check.

If the state header is missing or OutputValidity: INVALID appears, the output is diagnostic only and must not be executed or reused as previous state.
